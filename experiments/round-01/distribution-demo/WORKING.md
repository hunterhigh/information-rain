# 分发 Demo：基于节点选择的推荐机制推演

日期：2026-09-28
状态：待定方案；不是已批准规格或已实现功能

## 更准确的问题定义

这不是一般的“哪类作品点了喜欢”，而是：读者在一段具体的故事状态中，遇见了哪些可能的行动，选择了什么行动；这些有上下文的选择能否帮助我们估计读者愿意继续体验何种叙事机会。

当前内容格式已记录节点正文、可达分支、选项文案和结局，但选项本身没有结构化语义。`left/right/up` 是交互位置，不能作为选择含义。当前可以完整审计故事图，却不能只凭图结构读出选项所代表的处境、行动方式、价值取舍和后果。

因此，收藏、开始阅读、是否走到结局只是辅助信号；核心事件应是：**读者在给定故事前缀、看见这一组实际选项后，选择了其中哪一个。**这是该选项相对于同场其他选项的条件性选择证据，不等价于评分、满意度、稳定人格或道德立场。

## 现有结构盘点：哪些已经有算法价值

当前数据并非“完全没有可计算结构”，而是作品侧结构丰富、读者选择事件缺失。

| 已有结构 | 当前可计算的价值 | 不能据此直接推出 |
|---|---|---|
| 作品 `id`、标题、简介、作者、标签、时长、节点/结局数 | 基础候选过滤、作品相似度或多样性特征；标签与时长可用于冷启动展示 | 标签相同就代表体验相同；时长/规模就是质量 |
| 节点 `text`、`exits`、`labels` | 恢复故事图、选项集合、可达路径；文案可人工归纳决策语义 | `left/right/up` 是稳定选择含义；仅靠图边即可恢复价值取舍 |
| 结局 `isEnding`、`title`、`summary` 与结局正文 | 计算结局可达性、路径汇聚/分化；辅助人工检查分支后果 | 结局“好/坏”可以当用户奖励或偏好标签 |
| 本地 `exploredWorlds`、收藏、足迹、收集结局、总步数 | 作品层面的粗粒度进入/保存/完成信号 | 能还原用户如何走到结局，或提供跨用户热度 |
| 运行时 `pathHistory`、当前节点和选项移动逻辑 | 当前会话内已有记录 choice event 所需的大部分瞬时上下文 | 这些路径已持久化，或足以跨会话学习 |

因此有两种不同的算法资产：**故事图的结构特征现在就能离线计算**；**读者选择偏好需要新增持久化的事件记录，并连接作品侧选项语义**。前者可支持结构导航/候选多样性，后者才可能支持个性化。

## 待检验假说

这些是假说，不是已经验证的产品事实：

| 假说 | 机制解释 | 能削弱/推翻它的观察 |
|---|---|---|
| H1：有上下文的节点选择，比单纯收藏更早揭示读者的叙事兴趣 | 同一节点的选择是当时可见选项之间的相对偏好；跨故事可尝试匹配相似的取舍/行动机会 | 控制故事前缀和选项集合后，选择模式不能重复，或无法预测同类选择/区分候选 |
| H2：选择序列包含额外信号 | “观察→核实→行动”等路径顺序，可能表示读者偏好某类推进节奏，而不是单个行为标签 | 加入前序路径后，对后续选择没有稳定的增量解释力；效果完全由剧情结构决定 |
| H3：作品决策图谱可作为独立的内容侧推荐特征 | 分支度、路径深度、汇合点、可达结局差异等结构属性可帮助匹配探索密度或路径复杂度 | 结构特征和读者对体验的实际评价无关，或过度偏好复杂图而损害内容匹配 |
| H4：经审阅的选项语义可把局部选择迁移到跨作品推荐 | 行动方式、局部取舍、stake 等中性标注把一次具体选择连接到另一作品的“决策机会” | 标注者无法稳定达成一致，或理由虽一致但用户不认为候选贴近/有价值 |

H1 与 H4 最直接回答“如何围绕节点选择做推荐”；H2 是更复杂的后续模型；H3 可以先用现有数据算出，但只是作品结构特征，不是用户偏好本身。

## 从当前内容看见的可迁移信号

同样的方向位置在不同节点意义完全不同。例如：

- 《最后一班渡船》不断让读者权衡小满的具体承诺、更多受困者、救援速度与行动风险。
- 《第七次问询》让读者在观察/回应、如实承认/回避、核对事实/维持说法之间选择。
- 《白室二十四时》反复区分主动行动与持续观察、试探与验证。
- 关系题材的节点会出现直接表达、先倾听、延迟谈论或保持距离等关系推进方式。

这些例子说明，真正可能迁移的不是“喜欢某个题材”或“常按左键”，而是**对特定决策情境和叙事机会的兴趣**。还不能断言这些例子已足以组成一套通用的用户人格维度；字段要描述作品里发生的决策，而不是给读者下性格结论。

## 候选建模分层

### A. 保留选择原始事实

每次有效选择最少需要能够关联：

- 匿名的本地读者/试验会话 ID；
- `worldId`、`nodeId` 及到达当前节点的路径前缀；
- 当前确实展示的选项集合（稳定 `choiceId`，而非只存方向）；
- 最终选中的 `choiceId`；
- 选项集合的顺序/位置、事件序号；
- 之后是否继续、回看或完成该体验作为独立的后续事件，而非改写最初选择。

当前程序运行时有 `pathHistory`、当前节点与点击方向，可在用户选项时得到上游节点、实际方向、目标节点；但本地存储的足迹和结局不会保留完整路径或当时展示的其他选项。因此“原始事实”是建议新增的数据，而非声称 Demo 已经记录了它。

路径前缀是重要上下文：同一个汇合节点可能来自不同先前经历，故事的语气、读者期待与选择意义也可能不同。AAMAS 的 PBCF 互动叙事研究将偏好挂在“故事至今”的前缀而非孤立 plot point，正是因为片段评价会受到此前事件影响。该论文还使用故事片段的显式评分和多用户矩阵；本项目尚无这些数据，不能声称只记录选择就能复现其结果。

### B. 为可复用的选择加作品侧语义

当前 `labels` 是给读者看的自然语言，适合保留为原文；新加机器可读描述时，不应另造大量心理人格标签。建议先试一个小型、可组合的**选项语义标注**：

- `actionMode`：此选项要求读者做什么，如观察/查证、沟通/协商、揭示/隐瞒、保护/救援、冒险/撤离、等待/暂缓；
- `tradeoffs`：这次选择牵涉的局部取舍，如速度/安全、个体承诺/群体救援、信息/隐私、直接表达/关系缓冲；
- `stakes`：决定主要影响谁、什么资源或何种关系；
- `consequenceHorizon`：后果立刻显现，还是延后、跨节点累积。

不是每个选项都要填满每个字段；纯粹继续阅读/过渡的选项可标成低决策强度或不参与偏好更新。标签应中性、可追溯到原文，优先由编辑标注或机器预标后人工核验；不可仅靠词面情感、选项方向或结局“好坏”自动生成。

### C. 从选择学习偏好，而非先给用户分类

首个机制版本可以对同一节点展示的多个选项做**上下文成对比较**：选择 A 表示在当前情境下 A 胜过当时展示的 B/C，不代表 A 的行为类型在所有故事里永远胜过其他类型。把这些比较与选项语义结合，可形成低维、带不确定度、可随新选择修正的临时兴趣估计。

更合适的算法问题是 choice-based preference learning / pairwise ranking，而不是把它描述成传统点击率排序。新用户没有历史时，系统保持编辑/多样候选；随着本地选择逐渐增加，才可尝试个性化候选评分。早期规则模型要可解释、可重置；先验证标注和信号，不需引入 RecBole、LightFM、Gorse、Metarank 或 bandit 依赖。

### D. 从用户偏好映射到“作品体验机会”

推荐跨作品时，不能只汇总该作品全部选项的词频：读者一条路径不会读到所有支线，且每个选择的意义依赖前缀。可先离线为作品构建由节点图导出的**决策机会画像**，描述哪些类型的处境、行动方式、取舍和后果会出现，以及它们怎样沿可达路径形成序列；再让用户的选择偏好与这类机会画像匹配。

首个试验只需回答：对某个读者已体验的选择模式，哪些尚未体验的作品包含类似或互补的决策机会？推荐输出是一组候选并说明依据，而非预测或自动代选某个分支。内容图的拓扑、作品自身的因果与可达性仍由作者控制。

## 需要防止的误读和偏差

- **选择 ≠ 满意**：读者可能为了看后果故意选危险项，也可能对二选一都不满意。
- **选择 ≠ 人格**：不把“隐瞒一次”写成“欺骗型用户”，不作道德化或心理诊断标签。
- **结果 ≠ 偏好**：悲剧结局可能正是读者探索的体验，不应用结局“好坏”替用户打分。
- **未选 ≠ 不喜欢**：它只是在这一个选项集合和故事前缀里的相对落选。
- **曝光和顺序有影响**：需记录实际展示的完整选项和位置；若 UI 先后、文案长度或方向位置固定，模型会把呈现偏差当成选择倾向。
- **历史会影响理解**：同一节点/选项出现在不同路径前缀时，不应无条件合并。
- **不能夺走能动性**：选择倾向用于发现其他作品、解释候选；不应自动改写分支、隐藏可达选项或替人决定。

## Demo 阶段如何诚实验证

当前结论仍是两段式：

1. **现有 Demo 的所有者试用先保留基线。**它尚未验证内容和当前分发交互；偷偷改排序或收集画像会混淆反馈。
2. 如果项目所有者希望进一步验证此算法，再单独建可识别的选择研究模式，先在少数结构不同的作品中人工标注所有相关节点/选项，并征得本地试用者同意记录匿名选择。所有现有节点不需要一次性标注。

试验按顺序检查：

1. **标注是否可复现**：两位审读者能否对行动方式、取舍和 stakes 达成一致；分歧是否说明分类轴不自然？
2. **预测是否有信息量**：在相同选择情境/前缀下，暂存部分选项事件，观察模型能否预测被选的选项。此项只验证选择规律，不证明推荐体验更好。
3. **推荐是否有价值**：体验者看一组候选和推荐理由后，判断其是否贴近自己想体验的叙事机会，同时观察意外发现、多样性、控制感和是否感到被“看穿/定型”。与编辑精选或不个性化候选对照。
4. **再决定要不要学习算法**：只有出现足够多的不同读者、路径和可重复偏好反馈，才比较协同过滤、序列模型或 bandit；当前无法可靠计算通用离线指标或宣称提升。

这组实验中的合成读者只用于检查规则实现，不能充作市场证据。试验记录应限于本地、去标识并可清除；选择轨迹可能揭露敏感倾向，不能默认上传或用于广告画像。

## 结论

推荐机制有必要围绕分支故事数据来设计。比“点赞→相似作品”更贴近本项目的基础单位是**故事前缀 + 可见选项集合 + 选择结果 + 选项语义 + 后续体验反馈**。其中原始选择是条件偏好信号，选项标注把它连接到跨作品的“决策机会”；后续体验反馈才可以帮助判断推荐是否满足读者。

所以技术上可以在 demo 阶段做可验证原型，但现阶段不能把它伪装成学会人格或已经有效的推荐服务。当前最佳下一步不是接开源框架或改默认 Demo，而是先确认 choice-level 数据格式和一小组高质量人工标注，保留基线，再独立制作研究模式。
