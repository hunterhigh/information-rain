# 手机阅读滑动体验复核

日期：2026-09-30｜性质：体验诊断与方案讨论｜状态：设计待重新对齐

## 本次依据

- 当前活动产品是分发产品，读者页面在 `products/distribution/reader-web/`。
- 先前的[决定 0015：整屏作品切换与左右分支导航](../decisions/0015-full-screen-swipe-and-branch-navigation.md)记录了“TikTok 式作品流 + 故事内分支”的意图；本轮手机体验反馈表明，已部署交互没有达到该意图，需重新审视，而不是以“已实施”视为验收。
- 所有者反馈：阅读中上下切换内容不工作或不明显；进入作品后只看见左右分支，原先可选的第三个分支似乎丢失；切换时浮动文字框突兀，整体不顺。

## 核对出的现状

1. 内容图的出口数据支持 `left`、`right`、`up` 三个故事分支；例如「梦」的入口节点就配置了三个目标。
2. 手机分支提示栏只呈现左右选项。`up` 虽有出口，却只在拖动过程中进入单独的上方反馈元素，用户无法像左右分支一样预先看到它；这解释了“只剩左右”的直观感受。
3. 内容之间的纵向切换由舞台中的 Swiper 管理；同一个舞台还注册了另一套触摸监听器，把上划解释为故事 `up` 分支、下划解释为下一部作品。正文自身也可纵向滚动，并在滚动未到边界时拦截纵向导航。
4. 当前切换把舞台克隆为快照；拖动中隐藏真实内容并移动快照，释放后再等待约 100 毫秒渲染目标，旧快照随后独立滑出约 460 毫秒。方向提示是盖在舞台上的半透明浮层。由此会出现“提示浮在内容上、旧页离开、目标页之后才出现”的分段感，不是一个连续的页面运动。
5. 手机没有明确的第三分支提示，也没有清晰、始终一致的“当前阅读页 ↔ 相邻作品”纵向反馈。代码结构与用户感知的问题相吻合；因为尚未在真实设备逐步复现，本记录将具体触摸事件竞争视为高可能原因，而不是声称已锁定唯一运行时根因。

## 需求按阅读体验拆解

| 体验环节 | 用户要完成的事 | 目前的断点 | 目标体验 |
| --- | --- | --- | --- |
| 进入作品 | 看清正在读哪部作品、当前位置和可走方向 | 三个数据出口没有以同等清晰度出现 | 入口信息与可选路线一致；可达路线都能被发现 |
| 阅读正文 | 自然上下滚动，不误切作品或故事 | 正文滚动、上分支、作品流上下切换争用同一轴 | 读文字时滚动优先；离开正文区域或到达明确边界后才进入纵向导航 |
| 做故事选择 | 在当前节点走到另一个故事节点 | 左右有常驻文字，上分支藏在拖动浮层里 | 每个分支在动作前可理解；选择发生在内容内，不靠突兀提示框补救 |
| 浏览下一部作品 | 整页向上或向下切换，并能回看上一部 | 下划仅有自定义处理，Swiper 同时监听舞台；上一部/下一部的方向表达不完整 | 上、下方向都明确表示作品流移动，整屏直接跟手、释放后吸附到一页 |
| 完成切换 | 知道切换已成功并继续阅读 | 快照离场和目标页出现分两拍，伴随浮层文字 | 拖动时看到下一页从手势方向连续露出；提交后沿同一轨迹完成，取消时回弹 |

## 动作时间轴（目标节奏草案）

| 时间 | 手指与画面 | 交互反馈 | 流畅度要求 |
| --- | --- | --- | --- |
| 触点按下 | 页面保持静止 | 不弹提示、不预先跳内容 | 点击按钮、选中文字和滚动文本不被当成翻页 |
| 识别意图 | 约 8–12 px 后锁定主要方向（数值仍需真机调） | 只让一个方向的导航接手 | 水平分支与纵向作品流不可同时响应 |
| 持续拖动 | 当前页按手指位移连续移动；邻页从后方/边缘露出 | 目标标题可附着在将进入的页面边缘，不另叠黑色消息框 | 画面位移由同一手势控制，不先隐藏内容再动画快照 |
| 松手 | 位移/速度达到提交条件则继续到目标页，否则回到原位 | 不显示临时 toast；目标本身提供方向连续性 | 提交与回弹都只有一段连续动画 |
| 完成吸附 | 新页面稳定，滚动位置和文本状态重置到该节点预期位置 | 新作品或新节点的标题、作者、正文随页面一起到位 | 动画结束后不再延迟替换内容，快速连续手势有锁定/冷却 |

时长、距离阈值和惯性不能靠桌面模拟定稿；上表是体验目标，不是已批准的数值规格。

## 所有者提出的方向候选

所有者建议保留三个故事分支手势，并将下滑专用于进入下一部作品：

- **左滑、右滑、上滑**：分别进入当前节点对应方向的故事分支；
- **下滑**：整屏切换到下一部作品；
- 分支切换使用作品自身的光线或图像做方向提示，让画面仿佛被吸入所选方向；不使用箭头或悬浮文字框；
- 作品切换采用独立的整屏转场，让下一部作品完整接管舞台；
- 手机标题、作者、正文随所属阅读画面一起移动和离场，不能单独漂浮或残留。

这是一个有吸引力的候选，因为它保留了原内容图的三条故事路线，同时把下滑留给作品流。它接受方向语义不对称：上滑进入同一作品的故事节点，下滑离开当前作品。两类动作必须以明显不同的画面运动表达结果，用户才不会把“向上”误认为“回到上一部作品”。

### 体验上的具体含义

1. **分支手势从内容本身产生反馈。** 手指向左/右/上轻拖时，画面沿同一方向出现一道光、裂开的图像边缘或被牵引的局部纹理；拖动越深入，目标方向越明确。达成提交距离后，光与图像把旧节点吸入边缘，目标节点从这个开口延续出现；不够距离则自然归位。
2. **下一部作品是一整页接管。** 下滑时不显示分支选择的局部效果，当前作品让出整屏，下一部作品从连续的纵向运动中出现。完成后直接稳定在新作品，不叠加独立的提示框或延迟替换。
3. **无 `up` 出口时需要明确规则。** 上滑不能偷偷改成上一部作品，否则同一方向会因当前节点配置而改变含义。候选默认应是不执行故事跳转，并以轻微回弹表示没有该出口；若需要返回上一部作品，应另有稳定、可发现的回退入口，或由所有者决定另一种规则。
4. **正文滚动需要让位规则。** 在可滚动正文上，手指上下移动首先用于阅读；可选做法是只在图片/背景区域启动作品/分支纵向导航，或在正文到达滚动边界后才把继续拖动交给页面导航。两种做法需要真机对比误触率与可发现性。

### 体验时间轴补充

| 阶段 | 左/右/上分支 | 下滑切换作品 |
| --- | --- | --- |
| 方向锁定后 | 与当前节点图像相连的光或纹理向所选边缘流动 | 下一部作品的全屏画面从下方进入视野 |
| 持续轻拖 | 当前内容仍可辨认；边缘逐渐形成被吸入的开口或牵引轨迹 | 当前作品整体位移，邻近作品随手指露出，不出现文字框 |
| 松手达到条件 | 分支图像沿吸入方向完成转场，目标节点稳定落位 | 作品流吸附到下一整屏，更新标题与阅读内容 |
| 松手未达到条件 | 光线和图像回到原位，当前节点不变 | 下一页退回，当前整屏恢复 |

这些效果应由同一组方向与位移驱动，避免手指停止后画面才突然开始另一种动画。视觉实现可先用 GPU 友好的位移、遮罩和局部亮度变化；整屏实时模糊、复杂粒子或大面积滤镜不应成为首版依赖。

## 尚未决定

1. 是否采纳“左/右/上走分支、下滑进入下一部作品”的方向分工。
2. 上滑无对应分支时的反馈，以及上一部作品如何返回。
3. 纵向作品切换与长正文滚动的触点/边界规则。
4. 光线或图像吸入效果采用何种具体形态；需做可拖动原型后再看手感，而非先定纯静态效果图。
5. 真机验证后再定拖动阻尼、提交距离、速度阈值和回弹时长。

## 开源参考与可复用边界

| 参考 | 可借鉴之处 | 不宜直接照搬之处 |
| --- | --- | --- |
| [Swiper API](https://swiperjs.com/swiper-api)（项目已在使用） | 纵向整屏分页、阈值、速度、转场锁定、滑到边缘的处理；官方也强调嵌套 Swiper 的方向和事件边界要明确 | 目前问题正是 Swiper 与舞台自定义触摸监听重叠；再叠加另一个轮播库不会自动消除冲突 |
| [SwipeFeed](https://github.com/briansunter/swipefeed) | headless（只提供行为、不规定外观）的 feed 思路：统一轴锁、阈值/速度、滚轮与键盘输入、活动页状态及相邻项预载 | 它要求 React 19，而当前读者页是静态 HTML/原生 JavaScript；整包接入会引入前端框架迁移，不适合只为手势修补而引入 |

初步建议是借用成熟 feed 的“一个手势协调器 + 一个活动页 + 邻页预备 + 松手吸附”机制，不合并整套产品 UI 或 React 工具链。Swiper 可继续作为作品流动画器，也可在统一手势仲裁后只由代码调用其切页 API；关键是让同一触摸不会被 Swiper 和自定义处理器各自作决定。
