## 判断与建议

将当前提交标为首个**私有内部基线 `demo-v0.1.0`**，用目录级 `VERSION.md`、`CHANGELOG.md` 与 Git 标签建立可对比的版本记录。首次推送因网络连接失败暂缓，之后推送提交/标签并创建了 GitHub Release。此版本只证明某个源代码和内容快照可恢复，不代表项目所有者试玩通过、产品验收或公开发布许可。

迭代候选按信息价值排序：

1. **所有者真实试玩与逐篇内容体验记录。**先确认打开首屏、进入作品、跨作品切换、作品内选择、返回/继续、收藏与足迹的心智是否成立；记录愿意继续、困惑与中断的位置。它能决定下一步改内容、交互还是入口。
2. **移动端交互修正。**以真机检查 9:16 舞台、手势冲突、阅读时误切作品、结局后去向、文字换行/遮挡及减少动态效果；逐项将观察变成可验证修正，避免只凭静态设计稿判断。
3. **独立推荐研究模式（候选，须另行确认）。**沿用 `WORKING.md` 的“故事前缀 + 实际展示选项 + 选择结果”记录方案，在少数作品人工标注选择语义；保持主 Demo 推荐顺序不变，先测标注是否可复现与选择是否包含跨作品信息。此举涉及新的试验数据，不能视作已决定功能。
4. **内容授权与媒介扩展。**先分清私有展示范围、第三方 IP 与图片/音乐权利，再决定是否保留、替换或增加原创作品；插画及短视频作为后续媒介假设，不能用来跳过当前文字体验验收。

### 初步判断（供会议讨论）

1. 需要把“GitHub 仓库怎么管理项目”和“未来产品后端怎么运行”分成两个议题。前者现有结构能保存研究、实验和版本；后者仍是候选架构，不应因为仓库已在 GitHub 上就误以为产品已有服务端。

### 结构建议（待确认后实施）

- **技术愿景本体**：说明长期技术愿景中的对象、关系与假设；留在愿景/研究层，不能直接充当产品术语表。
- **分发产品本体**：定义用户、作品/世界、节点、可选方向、阅读路径、阅读会话、发现入口等产品实体，逐项标明对用户的含义、与技术愿景术语的关系、当前 Demo 中的呈现方式及尚未确定之处。它是产品文档和后续数据模型共用的业务词典。
- **产品路线图**：按阶段记录目标、进入条件、交付结果、验收证据、当前状态和依赖；路线图是滚动计划，不是一次冻结的承诺。初步建议阶段为：产品范围与本体 → 当前 Demo 基线和产品缺口 → 正式应用与托管数据架构 → 核心阅读/内容管理闭环 → 内部发布准备与上线；各阶段不代表已经批准具体功能或服务商。
- **工作基线**：集中回答“现在有效的是哪个产品、哪个版本、在哪个提交、当前做什么、还卡什么”。基线链接到路线图、决定、设计、内容、代码和日志，不复制这些材料的全文。
- **文档治理**：入口文档指引必读顺序；每份文档标明负责人/状态/日期或适用版本；决策记录解释为什么变；Changelog 记录每次可见版本改变；已撤回 Demo 与比较测试材料有归档索引和撤回原因。归档不等于删除，也不表示其仍然生效。
- **仓库节奏**：近期保持单 Git 仓库，先建立清楚的目录职责和引用规则，不急于拆仓库。开发设备不作为持久数据存储；产品需要的持续数据应进入正式托管环境，供应商与成本待路线图进入后端阶段再评估。
