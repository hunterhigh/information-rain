# 2026-09-29：从前端 Demo 到后端平台的架构参考会

## 会议目标

调研社交媒体、平台产品和互动叙事框架的开源架构，找出哪些抽象可以帮助 Information Rain 从本地前端 Demo 演进到可持续后端。

## 项目基线

- 当前分发 Demo 是单文件前端，23 部作品由内嵌内容与内容包注册产物组成；进度、收藏和路径尚无服务端持久化。
- 决定 0006 将工具产品与分发产品分开；“信息雨”是信息流方法，作品中的可达路径由内容决定。
- 账号、推荐/生成架构、内容创作工具如何连接、共享 API/数据库与正式发布地域仍未决定。
- 此会议聚焦架构材料和候选边界，没有批准技术栈、产品功能或部署方案。

## 新结论

1. **抽象存在于多个系统中，但未在抽样项目中找到完整同类成品。**互动叙事、用户数据与 feed、内容媒体流水线分别有成熟设计；没有发现单个项目同时解决分支作品图、路径恢复、跨作品发现和创作工具。
2. **最接近的信息流拆分是 AT Protocol。**PDS、Relay、App View、Feed Generator 分别持有权威记录、转送事件、提供查询/索引视图和提供排序策略；可借鉴职责分离，但先不实现 DID、跨站 Relay 或全球 App View。
3. **最接近作品运行时的是 Ink/Twine。**它们支持结构化分支内容、独立 renderer/runtime 和状态保存/导出；不提供用户、内容目录、权限和线上进度服务。
4. **真实平台说明后台职责会随媒体及社交目标增长。**Mastodon/Lemmy 包含身份、权限、API、feed/社交活动、审核和后台作业；PeerTube 进一步拆出对象存储、转码 worker 和远程 runner。这些应按需求逐项加入，不能因大平台使用就提前引入。
5. **Supabase 可作快速后端候选。**Postgres、Auth、Storage、API 和 Functions 可缩短首个服务端闭环；直接给浏览器访问数据库时必须有细致 RLS，服务端密钥不得下发。Directus 可作后台界面参考；其 v12 当前许可已变为 MSCL 1.0，且功能按许可等级区分，需核对当前使用条件，不能直接归为无限制开源选项。

## 当前建议（供后续讨论，不是决定）

以模块化单体为首期形态：版本化作品/节点/选择作为权威内容；阅读会话与路径独立存储；目录/搜索/精选作为发现模块；API 供现有前端调用；PostgreSQL 存结构化数据，对象存储放媒体。先让现有 23 部内容可重导入、可查询、进度可恢复。只有在上传处理、推荐索引或媒体转码出现实际工作量时才引入队列和独立 worker；只有跨服务传播需求明确后再评估 ActivityPub/AT Protocol。

这一方案的关键验收不只是“登录和 CRUD 成功”，而是内容版本变更后，已有会话仍能指向正确图版本；读者能按路径恢复；发现策略可以更换而不改内容 schema；选择事件默认受到明确同意、留存和删除规则约束。

## 未决问题

- 首期是否只做内容读取/阅读进度，还是同时做编辑后台？建议先完成前者。
- 内部试用要不要账号，还是暂用匿名/本地状态？需要在真实用户数据进入前决定。
- 选择 Supabase 托管、自托管或自建模块化 API/数据库；本轮仅形成候选，没有比较成本与托管合规细节。
- 工具产品和分发产品未来共用什么内容 schema、身份与权限；当前边界要求不先假设共享。
- 是否需要对外开放作者、上传、社区、评论、关注和联邦；这些都不是现有 Demo 必备能力。

## 后续恢复点

先由项目所有者确认首个后端最小范围（推荐：作品导入 + 目录/作品 API + 阅读进度恢复），再进行针对性技术选型和数据/API 设计。完整对照与一手来源保存在[架构参考调研](../../research/architecture/2026-09-29-platform-architecture-reference-survey.md)。
