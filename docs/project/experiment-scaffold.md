# 信息雨产品实验脚手架

状态：实验工作规范；2026-09-24 按[决定 0005](decisions/0005-content-first-demo.md)修订。2026-09-28 的[决定 0006](decisions/0006-two-products-and-medium-validation.md)进一步确定双产品结构及文字、插画、短视频渐进验证方向；本文原有「第一轮文字媒介」只约束当时的候选对比，不禁止单独导入原型的既有封面插画。本文规定如何研究、创作、制作、评审、试用和复盘产品，不预先决定任何 Demo 的机制或题材。

## 目标与边界

我们的任务是在信息雨、生成式世界与内容、推荐即生成之间，做出自己判断最有吸引力的产品形态。每一个候选都应是经过研究和推演后值得独立存在的产品，而不是为了隔离变量而有意削弱的对照组。项目所有者最终通过亲自体验决定其价值，并用具体体验指导迭代。第一轮计划约三个产品，但数量不是必须凑满的指标。

第一轮的共同条件沿用项目所有者已定边界：**手机优先、统一视觉设计语言、文字媒介**。统一视觉语言指共用色彩、字体、留白、质感与相同功能的操作反馈；各产品可以因机制不同而有不同的信息布局和移动方式。跨产品比较时记录初始入口、设备、视觉版本和内容量差异，避免把包装或文本数量误判为分发机制的效果。

本文件只建立实验脚手架。旧计划中的 R01-B 单轴个性化信息流已被项目所有者排除，不继续设计或制作。替代产品必须经外部研究和产品推演后选择。旧计划中的 A/C 也不是已批准规格；不能从旧文档直接开工。

“实验脚手架”包括：外部研究与第一性原理推演、设计文档标准、讨论与决策节奏、产品机制 Demo 的阶段门、内容体验的制作标准、试用记录、下一轮指令、文件组织以及 Agent 工作约束。产品故事、信息走向、具体算法和技术栈要由逐个产品设计产生。

## 实验单位与顺序

一轮实验由若干个**产品候选**组成。每个候选先经过外部研究、推演和压力测试，由 Agent 同时说清产品为何值得打开、具体内容为何值得继续，以及多走向结构对该内容增加了什么。之后先创作可独立阅读的内容样本，再做直接进入内容的可操作 Demo，并分别评审内容、产品体验和软件行为。项目所有者实际体验后再决定是否扩展。一个候选对应 `研究与推演 → 产品与内容命题 → 内容初稿和独立审读 → 最小可操作 Demo → 分层评审与修订 → 所有者试用 → 迭代判断`。

```text
项目愿景与外部信息收集
  → 市场需求、相邻产品、技术能力与限制的证据整理
  → 第一性原理拆解、关系推演、候选形成与压力测试
  → Agent 提出产品承诺、代表性内容与两者为什么相互需要
  → 为该 Demo 写创作简报与内容初稿，先脱离界面审读
  → 用最少界面承载内容，第一屏直接进入体验
  → 分别检查创作质量、产品价值、交互规则与软件行为并修订
  → 项目所有者试用与记录
  → 根据真实体验决定是否扩展为三种正式内容体验或完整设计
  → 跨产品比较、下一轮指令
```

后一步不能拿来补前一步的缺口：好看的故事不能独自证明分发产品成立；可点击的路径也不能代替值得读的内容。中性文字、占位符和规则说明可用于**内部机制测试**，不得作为交给项目所有者评价产品的 Demo。面向体验者的 Demo 必须是一段真正可消费的代表性内容；对叙事候选，它应像作品而不是产品说明书。内容可以表达人物、处境、事件、发现与后果，不必用旁白解释“你现在能否改选”。

## 阶段门

| 阶段 | 必需产物 | 可以进入下一阶段的条件 |
| --- | --- | --- |
| S0 脚手架 | 本规范、Agent 规则、模板与轮次登记 | 版本、状态和文件责任清楚 |
| S1 信息与推演 | 每个候选的外部研究、来源记录、原始事实与约束、推演草稿和压力测试 | Agent 能基于证据解释为何选择该产品，而非只给出凭空创意；被排除的想法不占名额 |
| S2 产品与内容命题 | 每个 Demo 的 `DEMO-BRIEF.md` 与可脱离界面阅读的 `CONTENT-DRAFT.md`；机制约束可另记 `MECHANISM.md` | 说得清用户为了什么而进入和继续、内容独立的吸引力、多走向为何必要；脱离界面审读时没有产品自述或规则讲解冒充内容 |
| S3 可操作 Demo | 手机尺寸可进入的代表性内容与最少必要操作 | 打开即进入内容，不先进入营销页、实验目录或机制教程；内容与选择能形成真实体验，而非仅演示状态转移 |
| S4 分层评审 | 功能测试、内容审读、产品体验自评与记录 | 分别给出结论；不能用测试通过或画面精致推定内容有趣、产品有价值，明显不合格则修订或撤回 |
| S5 所有者试用 | 带版本的原始轨迹和即时反馈 | 仅将真实发生的体验写成所有者判断；自评不冒充试用 |
| S6 后续内容与产品判断 | 若值得扩展，制作三种正式内容体验并各自计时；跨产品比较与下一轮指令 | 正式内容每种至少十分钟；结论忠实反映实际体验 |

进入阶段是工作顺序，不表示要为每个细节寻求形式化批准。Agent 自行制作和评审 Demo；这不等于项目所有者已认可机制。只有实际试用才产生所有者体验判断。

## 每个产品的研究与推演

每次设计都由 Agent **主动进行外部搜索**，独立挑选有判断价值的材料，再决定哪些信息进入设计。项目所有者给出的想法是重要的探索方向，不是市场或技术结论。至少覆盖三类材料：市场需求与实际消费行为、相邻或替代产品的做法和表现、相关生成与分发技术的一手资料。市场资料需留意样本、口径、地域和时间；技术事实优先查官方文档、论文或可复现的一手演示。搜索不是收集支持初衷的例子；有冲突的证据要一并处理。每个重要判断在研究笔记中保留链接、日期、摘取的事实、可信度和采用或排除理由。

先形成 `RESEARCH.md`，再在 `WORKING.md` 中推演；随后用每个 Demo 的 `DEMO-BRIEF.md` 连接产品命题与创作上下文。若有复杂规则，另用 `MECHANISM.md` 记录内部实现；若后续需要完整长文，再整理 `DESIGN.md`。这些文件职责不同：

- `RESEARCH.md` 保存外部来源、原始观察、可核实的数字、用户提出的材料及资料之间的冲突。不从搜索结果标题直接推断市场需求。
- `WORKING.md` 保存思考草稿：拆分事实、原则、目标、假设、未知和设计选择；建立注意力、信息供给、分发、生成成本、时延、状态与用户行为之间的关系；推导若干真正不同的产品机制，比较后作出选择。可以有被否决的思路和未成熟的公式，不能用假精度包装判断。
- `DEMO-BRIEF.md` 分开记录产品想给人的价值与具体内容的创作依据、作品目标、人物或信息张力、表达方式和不应出现的产品自述；它不是要放进界面的文案。
- `MECHANISM.md` 若需要则记录实现约束、内容如何声明可达方向与状态后果；不得替创作简报决定人物、事件或作品价值。`DESIGN.md` 是可选的长文整理版本，不是 Demo 开工许可证。

压力测试服务于增强产品，不是预设其失败。至少考虑极端的内容广度、连续快速移动、重复和质量下降、生成延迟与成本、用户兴趣变化，以及产品自身最重要的状态或信息关系在边界条件下如何维持。发现薄弱点后优先修改设计；如果技术上暂不可达，标明 Demo 如何模拟、哪些体验判断不能由模拟得出。Agent 最终必须给出自己的取舍，而不是把未经分析的选项清单交给项目所有者。

## 若制作完整设计文档，其最低标准

每个产品使用独立的 `DESIGN.md`，正文至少 **10,000 个汉字**；其中“市场需求与使用行为”和“技术理解”两部分合计至少 **3,000 个汉字**。用 `node scripts/check-experiment-design.mjs <产品 DESIGN.md>` 统计；脚本排除标题、代码块、表格和纯引用。不能靠重复句子、堆术语或大段粘贴 README 达标。汉字计数用于防止草率，并不取代研究与设计质量。建议正文目标为 10,000–13,000 字，超出时优先删冗余而不是删关键机制。

市场需求部分关注更大的需求结构：人们把注意力花在何种娱乐和信息体验上，现有产品验证了哪些消费行为，内容供给和分发怎样限制或释放需求，哪些可观察信号支持潜在市场。它可以分析个人使用情境，但不能把“用户为什么打开这个产品”当成整段需求分析。技术部分讨论现实能力与限制，以及它们怎样改变产品结构。两部分都要基于外部资料和清晰推断；不把“用户喜欢新奇感”“模型会越来越快”这种未经观察的句子写成事实。引用靠近支持的判断，来源和日期可追溯。

最终文档使用自然的技术博客语言：段落围绕问题、证据、推理、决策展开，避免内部项目管理术语和逐条填写问卷的口吻。为便于篇幅检查，保留以 `## 1.` 开头的市场需求章节和以 `## 2.` 开头的技术理解章节；其他章节标题、顺序和篇幅由产品逻辑决定。以下是覆盖范围，不是固定目录或逐章字数配额：

- 市场需求、相邻产品和技术演进怎样共同创造机会；哪些观察可靠，哪些仍是推断。
- 从底层事实与约束怎样推导到这个产品，其他值得考虑的方案为什么不如它。
- 信息单元如何出现，用户如何接收和进入多个可能的信息走向；连续使用十分钟会发生什么。
- 需要什么状态、推荐和生成能力；手机交互如何承载；当前如何做出机制 Demo，真实实现有哪些难点。
- 产品在边界条件下经过了哪些压力测试，设计如何修改；最后 Agent 为什么仍判断它是值得做的最强方案。

### 有实际体验后的讨论主题

Agent 先独立研究、推演、产出 Demo 并自评。项目所有者实际体验后的讨论可围绕以下四个主题展开；一次对话可以跨越多个主题。讨论中的纠正写入当前工作文件，必要时再整理成长文。

1. **市场与需求判断**：展示外部观察和对市场需求的推断，讨论哪些机会重要、哪些材料不足。项目所有者的使用愿望是重要线索，但不替代市场研究。
2. **产品推演**：展示从基本事实、约束和关系推导出的产品结构，用具体场景模拟用户接触一片信息、选择走向、到达新位置的过程。让项目所有者指出与愿景不符或缺乏吸引力的地方。
3. **技术与压力测试**：展示外部技术资料、当前能力与模拟边界，并把产品放入高频使用、内容暴增、延迟、重复和状态变化等情境，现场推演改进。
4. **方案选择与表达**：Agent 说明为什么最终选择这一版而非其他认真考虑过的方案；项目所有者指出仍有误解的地方。修订后形成最终技术博客式文档。

讨论是用来提高产品判断，不是一份要求项目所有者填写的固定问卷。Agent 要主动搜索、主动选择和主动提出方案。

### 多后继的开放定义

信息雨的本体是**当前位置存在多个可到达的信息走向**。设计必须让读者理解：系统如何提供这些可能、用户怎样感知和进入它们、到达新位置后下一片信息怎样形成。这些关系可以稳定、临时、强相关、弱相关，甚至不依赖相邻内容的逻辑关系；方向也可以只是界面入口，不必承担时间、人物、题材或因果含义。

脚手架不规定后继数量、方向数量、手势语义、内容关联、是否回退、候选生成时机或空间隐喻。每个产品在研究与推演后自行选择。设计文档需把**自己实际选择的机制**讲到读者能想象操作和实现的程度，并说明这个选择如何产生娱乐价值；不必回答一份穷尽所有可能形态的协议清单。已被排除的单轴 R01-B 不能再以“对照组”为由复活。

项目所有者进一步确认：产品应尽量给予自由度，允许具体内容决定返回旧位置后能否进入当时未选的方向，以及其他可达路径与后果。机制设计要说明产品提供哪些承载能力、内容怎样表达自己的规则、用户怎样通过情境、后果和必要的交互反馈理解规则；不要求作品中的叙述者讲解产品机制。某次试验采用的候选数、预览、回退或保存方式只是该次内容与版本的配置，不得写成所有内容通用的产品限制。决定见[0003](decisions/0003-content-defined-trajectories.md)。

## 用户可消费的 Demo：产品与内容共同工作

产品端先回答：什么人在什么情境下打开，实际得到什么，而不是我们想证明哪一种机制？什么让他愿意继续、下次回来，甚至投入更多时间或金钱？信息雨的多走向相对线性阅读、普通内容列表增加了什么体验？这些是需通过行为与反馈检验的产品和商业假设，不是 Agent 可以自评证明的商业价值。对于叙事候选，作品本身必须有阅读价值；对于非叙事候选，也必须有其自身的消费价值，不能把选择按钮当价值。

内容端为**每个 Demo**写创作简报，不使用所有题材通用的固定故事公式。叙事样本要有具体处境和读者关心后续的理由；人物欲望、变化、悬念、冲突或发现是可能的来源，而非必须逐项填满的清单。非叙事样本也要明确它让人发现、理解或感受到什么。简报给创作者足够上下文与创作原则，但不把人物行动、走向数量、文风或结局写成平台级规定。创作可包含分叉的内容初稿，脱离界面审读各片段及其关系；不要求先写线性故事再补选项，也不要为三个技术边界案例硬编三段空泛的故事。

面向读者的文字只服务作品。不得用“未选方向仍在”“旧快照可看”“你的路径会被记录”等规则说明冒充叙事或信息内容。规则、状态和历史权限由内部内容定义与界面处理；必要的操作提示应短、就地、可理解，并与正文分开。不能为了隐去规则让用户误以为不可逆动作可以撤销；简洁要保留重要后果的辨认能力。

Demo 默认**打开即进入内容**，不设官网式 hero、产品口号、实验目录或机制教程作为体验入口。若某候选确实需要入口选择，应说明它完成的用户任务，并保持最少界面。统一视觉语言服务阅读与选择，不以装饰或“设计感”替代价值。手机第一屏要检查体验者实际先看到什么，而不是只检查响应式尺寸。

内部可使用中性测试材料验证引擎、状态和边界；这类材料与面向项目所有者的产品 Demo 分开命名和评审。对外 Demo 不必一开始达到正式内容体验的十分钟，但必须足以产生真实的阅读或消费过程、至少一次有意义的展开与后果；几句短文和状态标签不能承担产品判断。只有 Demo 经分层评审、所有者实际试用并决定继续扩展后，才设计三种正式内容形式。

后续每种正式内容形式有独立 `CONTENT-01/02/03.md`，写明形式命题、适合该产品机制的原因、与另外两种的实质差异、内容单元规则、内容生产和更新方法、试用路径、失败风险。第一轮全部使用文字；“三种内容形式”不是文字、图片、视频三种媒介。

### 分层评审，不用一项通过代替另一项

1. **作品审读**：暂时移去界面和规则说明，只读内容。是否有可感知的事件、信息或变化？每一步是否提供新东西？读者是否有内容本身带来的继续理由？若没有，先改内容，不继续打磨界面。
2. **产品体验**：首次打开是否直接进入价值？多走向是否给这段内容带来线性版本没有的可能，而非把下一章排成菜单？文字、操作、反馈是否足够简洁？评审者应从读者视角实际走完路径，指出失去兴趣的具体位置。
3. **行为与技术**：用测试检查可达方向、状态转移、历史权限、错误路径、手机尺寸与运行异常。测试通过只说明实现兑现规则，不说明产品或内容成立。
4. **证据与结论**：把自动检查、创作审读、Agent 的主观判断和项目所有者的真实反馈分开记录；模拟推荐或生成必须如实标注。明显缺乏内容价值或产品目的的 Demo 标为失败或内部样本，不交给所有者当合格产品试用。

### 十分钟有效体验的判定

“十分钟”指正常阅读和操作节奏下，用户能够连续获得至少十分钟有变化、有选择或有发现的体验。不能用强制等待、循环旧节点、重复换词、冗长空文案或人为放慢动画凑时长。设计时以约十二至十五分钟的有效材料为容量目标，写出预期路径、内容单元数、分支覆盖与估算依据；制作后进行真实计时走查，记录起止、主动操作时间、已见过的重复内容与提早终止点。若正常走查在十分钟前耗尽新内容，应补足后重新验证。

每个产品三种形式至少对应约三十分钟可试用材料；三个产品总量可分次试用，不能要求项目所有者一次完成全部。内容体验不足十分钟时标为未完成，不进入正式比较。

## 试用记录与证据链

每个机制试用和内容试用都保留三层记录：

- **原始轨迹**：版本、设备、开始与结束、可见且可执行的候选、选择、内容允许的返回动作、停留、错误、实际展示的文本与状态摘要。只记录实验需要的信息。
- **项目所有者的即时反馈**：定位到某一刻或节点，写他看见什么、做了什么、想要什么、为什么想继续或退出；允许口述后整理，但保留原话。
- **分析与指令**：结合项目所有者的实际体验，解释什么创造了价值、什么削弱了价值，决定下一轮保留、加强、修改或放弃什么。

试用可以包括首次接触、理解机制后的自由探索和隔一段时间再进入；不要求项目所有者遵守严格的实验室顺序。记录重点是实际被什么吸引、想去哪里、什么时候失去兴趣。若机制或内容在试用中改版，记录必须带版本，不能把不同版本的反馈无标记合并。

每轮结束形成 `RESULT.md`：项目所有者对各产品及其内容体验的具体判断、跨产品比较、关键体验片段、Agent 的分析，以及明确的迭代指令。研究和压力测试帮助我们把产品做强，最终成败以项目所有者的实际体验为准。下一轮 `PLAN.md` 应能追溯到这些指令。原始反馈不因新结论而覆盖。

## Agent 工作约束

项目级 `AGENTS.md` 把这些约束写成可执行规则：从当前 README、脚手架、轮次计划和上一轮结果恢复上下文；每次产品设计主动外部搜索，先整理证据，再第一性原理推演和压力测试，自己作出产品选择；每个 Demo 先有产品与内容创作简报及内容初稿，随后自主产出可操作体验并分层评审；记录原始反馈并产生下一轮指令；模拟推荐与生成必须如实标注；不擅自接入付费模型、外部服务、真实用户数据或部署。若另行制作完整 `DESIGN.md`，才执行该文档的篇幅检查。

Agent 不应因文档达到字数就宣布产品已设计完成。若市场判断缺乏外部材料、机制解释不清、技术判断无依据、内容形式由题材而非产品结构驱动，需继续研究、推演与修改。项目所有者的纠正应写回当前有效文档；旧版设想不再自动成为实现依据。
