# 信息雨产品实验脚手架

状态：实验工作规范；2026-09-23。本文规定如何研究、设计、制作、试用和复盘产品，不预先决定任何 Demo 的产品机制或内容题材。

## 目标与边界

我们的任务是在信息雨、生成式世界与内容、推荐即生成之间，做出自己判断最有吸引力的产品形态。每一个候选都应是经过研究和推演后值得独立存在的产品，而不是为了隔离变量而有意削弱的对照组。项目所有者最终通过亲自体验决定其价值，并用具体体验指导迭代。第一轮计划约三个产品，但数量不是必须凑满的指标。

第一轮的共同条件沿用项目所有者已定边界：**手机优先、统一视觉设计语言、文字媒介**。统一视觉语言指共用色彩、字体、留白、质感与相同功能的操作反馈；各产品可以因机制不同而有不同的信息布局和移动方式。跨产品比较时记录初始入口、设备、视觉版本和内容量差异，避免把包装或文本数量误判为分发机制的效果。

本文件只建立实验脚手架。旧计划中的 R01-B 单轴个性化信息流已被项目所有者排除，不继续设计或制作。替代产品必须经外部研究和产品推演后选择。旧计划中的 A/C 也不是已批准规格；不能从旧文档直接开工。

“实验脚手架”包括：外部研究与第一性原理推演、设计文档标准、讨论与决策节奏、产品机制 Demo 的阶段门、内容体验的制作标准、试用记录、下一轮指令、文件组织以及 Agent 工作约束。产品故事、信息走向、具体算法和技术栈要由逐个产品设计产生。

## 实验单位与顺序

一轮实验由若干个**产品候选**组成。每个候选先经过外部研究、第一性原理推演和压力测试，再形成一份经多轮讨论与整理的完整产品设计。之后制作可操作的**产品机制 Demo**，最后基于该机制制作三种**内容体验**。因此，一个候选对应 `研究与推演 → 设计 → 机制 Demo → 三种内容体验 → 项目所有者试用 → 产品判断`。

```text
项目愿景与外部信息收集
  → 市场需求、相邻产品、技术能力与限制的证据整理
  → 第一性原理拆解、关系推演、候选形成与压力测试
  → Agent 选择自己认为最好的产品方案并说明理由
  → 与项目所有者多轮讨论，修改草稿
  → 整理成不少于一万字的技术博客式设计文档
  → 产品机制 Demo
  → 机制试用与修正
  → 每个产品三种内容体验（每种至少十分钟）
  → 项目所有者试用与记录
  → 项目所有者的体验判断、跨产品比较、下一轮指令
```

后一步不能拿来补前一步的缺口。例如，内容题材不能代替对信息移动规则的解释；一个好看的故事不能证明分发产品成立。产品机制 Demo 可以使用中性的测试内容来让操作可见，但不把测试内容当成已设计好的内容形式。

## 阶段门

| 阶段 | 必需产物 | 可以进入下一阶段的条件 |
| --- | --- | --- |
| S0 脚手架 | 本规范、Agent 规则、模板与轮次登记 | 版本、状态和文件责任清楚 |
| S1 信息与推演 | 每个候选的外部研究、来源记录、原始事实与约束、推演草稿和压力测试 | Agent 能基于证据解释为何选择该产品，而非只给出凭空创意；被排除的想法不占名额 |
| S2 产品设计 | 每个产品独立的完整设计文档，以及与项目所有者的多轮讨论记录 | 达到篇幅与内容门槛；清楚说明产品体验和信息如何移动；最终稿有完整论证而非拼接笔记 |
| S3 产品机制 Demo | 可在手机尺寸操作的分发与移动机制；中性测试内容 | 核心路径、边界操作、回退与记录可操作；已由项目所有者实际试用机制 |
| S4 内容体验 | 每个产品三种不同内容体验及各自说明 | 每一种都提供至少十分钟有效体验，并在该产品机制上运行 |
| S5 体验判断 | 原始记录、项目所有者的判断、跨产品比较、下一轮指令 | 结论忠实反映实际体验；下一轮工作由项目所有者的反馈和我们对产品的分析产生 |

进入阶段是工作顺序，不表示要为每个细节反复寻求形式化批准。项目所有者明确要求逐个产品进行详细讨论，因此 S2 到 S3、S3 到 S4 的转换必须经过真实的产品讨论和试用；不能由 Agent 自行假定用户已经认可某个机制。

## 每个产品的研究与推演

每次设计都由 Agent **主动进行外部搜索**，独立挑选有判断价值的材料，再决定哪些信息进入设计。项目所有者给出的想法是重要的探索方向，不是市场或技术结论。至少覆盖三类材料：市场需求与实际消费行为、相邻或替代产品的做法和表现、相关生成与分发技术的一手资料。市场资料需留意样本、口径、地域和时间；技术事实优先查官方文档、论文或可复现的一手演示。搜索不是收集支持初衷的例子；有冲突的证据要一并处理。每个重要判断在研究笔记中保留链接、日期、摘取的事实、可信度和采用或排除理由。

先形成 `RESEARCH.md`，再在 `WORKING.md` 中推演，最后整理 `DESIGN.md`。这三个文件职责不同：

- `RESEARCH.md` 保存外部来源、原始观察、可核实的数字、用户提出的材料及资料之间的冲突。不从搜索结果标题直接推断市场需求。
- `WORKING.md` 保存思考草稿：拆分事实、原则、目标、假设、未知和设计选择；建立注意力、信息供给、分发、生成成本、时延、状态与用户行为之间的关系；推导若干真正不同的产品机制，比较后作出选择。可以有被否决的思路和未成熟的公式，不能用假精度包装判断。
- `DESIGN.md` 是向项目所有者提交的整理后版本：像技术博客一样从现实问题出发，引用关键证据，逐步讲清推演、设计选择、系统如何工作和为什么这个方案最好。它不是把原始笔记、问答和来源列表原样拼接起来。

压力测试服务于增强产品，不是预设其失败。至少考虑极端的内容广度、连续快速移动、重复和质量下降、生成延迟与成本、用户兴趣变化，以及产品自身最重要的状态或信息关系在边界条件下如何维持。发现薄弱点后优先修改设计；如果技术上暂不可达，标明 Demo 如何模拟、哪些体验判断不能由模拟得出。Agent 最终必须给出自己的取舍，而不是把未经分析的选项清单交给项目所有者。

## 每个产品设计文档的最低标准

每个产品使用独立的 `DESIGN.md`，正文至少 **10,000 个汉字**；其中“市场需求与使用行为”和“技术理解”两部分合计至少 **3,000 个汉字**。用 `node scripts/check-experiment-design.mjs <产品 DESIGN.md>` 统计；脚本排除标题、代码块、表格和纯引用。不能靠重复句子、堆术语或大段粘贴 README 达标。汉字计数用于防止草率，并不取代研究与设计质量。建议正文目标为 10,000–13,000 字，超出时优先删冗余而不是删关键机制。

市场需求部分关注更大的需求结构：人们把注意力花在何种娱乐和信息体验上，现有产品验证了哪些消费行为，内容供给和分发怎样限制或释放需求，哪些可观察信号支持潜在市场。它可以分析个人使用情境，但不能把“用户为什么打开这个产品”当成整段需求分析。技术部分讨论现实能力与限制，以及它们怎样改变产品结构。两部分都要基于外部资料和清晰推断；不把“用户喜欢新奇感”“模型会越来越快”这种未经观察的句子写成事实。引用靠近支持的判断，来源和日期可追溯。

最终文档使用自然的技术博客语言：段落围绕问题、证据、推理、决策展开，避免内部项目管理术语和逐条填写问卷的口吻。为便于篇幅检查，保留以 `## 1.` 开头的市场需求章节和以 `## 2.` 开头的技术理解章节；其他章节标题、顺序和篇幅由产品逻辑决定。以下是覆盖范围，不是固定目录或逐章字数配额：

- 市场需求、相邻产品和技术演进怎样共同创造机会；哪些观察可靠，哪些仍是推断。
- 从底层事实与约束怎样推导到这个产品，其他值得考虑的方案为什么不如它。
- 信息单元如何出现，用户如何接收和进入多个可能的信息走向；连续使用十分钟会发生什么。
- 需要什么状态、推荐和生成能力；手机交互如何承载；当前如何做出机制 Demo，真实实现有哪些难点。
- 产品在边界条件下经过了哪些压力测试，设计如何修改；最后 Agent 为什么仍判断它是值得做的最强方案。

### 每个产品固定的讨论节奏

设计文档不能由 Agent 关起门来一次写完，再让项目所有者只看成品。Agent 先独立研究、推演并提出明确判断，然后围绕以下四个主题与项目所有者反复讨论；一次对话可以跨越多个主题，也可以因新资料返回前一主题。讨论中的纠正写入草稿，最终稿再整理成连贯文章。

1. **市场与需求判断**：展示外部观察和对市场需求的推断，讨论哪些机会重要、哪些材料不足。项目所有者的使用愿望是重要线索，但不替代市场研究。
2. **产品推演**：展示从基本事实、约束和关系推导出的产品结构，用具体场景模拟用户接触一片信息、选择走向、到达新位置的过程。让项目所有者指出与愿景不符或缺乏吸引力的地方。
3. **技术与压力测试**：展示外部技术资料、当前能力与模拟边界，并把产品放入高频使用、内容暴增、延迟、重复和状态变化等情境，现场推演改进。
4. **方案选择与表达**：Agent 说明为什么最终选择这一版而非其他认真考虑过的方案；项目所有者指出仍有误解的地方。修订后形成最终技术博客式文档。

讨论是用来提高产品判断，不是一份要求项目所有者填写的固定问卷。Agent 要主动搜索、主动选择和主动提出方案。

### 多后继的开放定义

信息雨的本体是**当前位置存在多个可到达的信息走向**。设计必须让读者理解：系统如何提供这些可能、用户怎样感知和进入它们、到达新位置后下一片信息怎样形成。这些关系可以稳定、临时、强相关、弱相关，甚至不依赖相邻内容的逻辑关系；方向也可以只是界面入口，不必承担时间、人物、题材或因果含义。

脚手架不规定后继数量、方向数量、手势语义、内容关联、是否回退、候选生成时机或空间隐喻。每个产品在研究与推演后自行选择。设计文档需把**自己实际选择的机制**讲到读者能想象操作和实现的程度，并说明这个选择如何产生娱乐价值；不必回答一份穷尽所有可能形态的协议清单。已被排除的单轴 R01-B 不能再以“对照组”为由复活。

## 产品机制先于内容形式

`MECHANISM.md` 将最终产品设计转为可执行的结构：信息单元如何呈现、有哪些可达走向、用户如何行动、系统怎样响应、哪些状态需要维护。产品 Demo 先把信息分发形态做出来，可以使用足以展现体验的临时文字材料；此时不提前锁定三种正式内容形式。机制试用关注用户能否感到这一产品值得继续使用，以及信息移动本身带来的价值。机制 Demo 不应是只有按钮和占位符的空壳。

只有机制 Demo 经试用后，才为该产品设计三种内容形式。内容形式由产品机制决定：同一个分发产品怎样容纳不同类型的信息单元、节奏和价值。不能先写三套故事，再为它们补一个共同 UI。三种形式需在结构上有可解释差异，例如信息颗粒度、关联强度、时间跨度、交互后果或消费节奏；不能只是换三个题材、三组角色或三种文风。具体三种形式留到产品机制确定以后再设计。

每种内容形式有独立 `CONTENT-01/02/03.md`，写明形式命题、适合该产品机制的原因、与另外两种的实质差异、内容单元规则、内容生产和更新方法、试用路径、失败风险。第一轮全部使用文字；“三种内容形式”不是文字、图片、视频三种媒介。

### 十分钟有效体验的判定

“十分钟”指正常阅读和操作节奏下，用户能够连续获得至少十分钟有变化、有选择或有发现的体验。不能用强制等待、循环旧节点、重复换词、冗长空文案或人为放慢动画凑时长。设计时以约十二至十五分钟的有效材料为容量目标，写出预期路径、内容单元数、分支覆盖与估算依据；制作后进行真实计时走查，记录起止、主动操作时间、已见过的重复内容与提早终止点。若正常走查在十分钟前耗尽新内容，应补足后重新验证。

每个产品三种形式至少对应约三十分钟可试用材料；三个产品总量可分次试用，不能要求项目所有者一次完成全部。内容体验不足十分钟时标为未完成，不进入正式比较。

## 试用记录与证据链

每个机制试用和内容试用都保留三层记录：

- **原始轨迹**：版本、设备、开始与结束、可见候选、选择、回退、停留、错误、实际展示的文本与状态摘要。只记录实验需要的信息。
- **项目所有者的即时反馈**：定位到某一刻或节点，写他看见什么、做了什么、想要什么、为什么想继续或退出；允许口述后整理，但保留原话。
- **分析与指令**：结合项目所有者的实际体验，解释什么创造了价值、什么削弱了价值，决定下一轮保留、加强、修改或放弃什么。

试用可以包括首次接触、理解机制后的自由探索和隔一段时间再进入；不要求项目所有者遵守严格的实验室顺序。记录重点是实际被什么吸引、想去哪里、什么时候失去兴趣。若机制或内容在试用中改版，记录必须带版本，不能把不同版本的反馈无标记合并。

每轮结束形成 `RESULT.md`：项目所有者对各产品及其内容体验的具体判断、跨产品比较、关键体验片段、Agent 的分析，以及明确的迭代指令。研究和压力测试帮助我们把产品做强，最终成败以项目所有者的实际体验为准。下一轮 `PLAN.md` 应能追溯到这些指令。原始反馈不因新结论而覆盖。

## Agent 工作约束

项目级 `AGENTS.md` 把这些门槛写成可执行规则：从当前 README、脚手架、轮次计划和上一轮结果恢复上下文；每次产品设计主动外部搜索，先整理证据，再第一性原理推演和压力测试，自己作出产品选择；通过多轮讨论整理最终文档；不跳过一万字及三千字要求；先机制 Demo，后内容；每产品三种有效十分钟体验；记录原始反馈并产生下一轮指令；模拟推荐与生成必须如实标注；不擅自接入付费模型、外部服务、真实用户数据或部署。

Agent 不应因文档达到字数就宣布产品已设计完成。若市场判断缺乏外部材料、机制解释不清、技术判断无依据、内容形式由题材而非产品结构驱动，需继续研究、推演与修改。项目所有者的纠正应写回当前有效文档；旧版设想不再自动成为实现依据。
